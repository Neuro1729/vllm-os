# Benchmarking methodology

**No GPU benchmark results exist in this repository.** The pipeline has been validated only on CPU (plan generation, replay with a fake engine, report generation from synthetic fixtures). Every number in a real report must come from a run on a GPU machine.

## Variants

| Variant | What it is | Engine |
|---|---|---|
| `v0` | original nano-vLLM at commit `e1da1f5`, unmodified | separate worktree on `PYTHONPATH` |
| `fcfs` | modernized unified scheduler, FCFS | this repo, `scheduling_policy="fcfs"` |
| `mlfq` | MLFQ without proactive preemption | `scheduling_policy="mlfq"`, `enable_mlfq_preemption=False` |
| `mlfq_preempt` | full MLFQ with selective preemption | `enable_mlfq_preemption=True` |

The main comparison is `fcfs` against `mlfq` and `mlfq_preempt`, which use identical execution code. `v0` differs in execution code as well, so its gap to `fcfs` is not attributable to the scheduling policy.

V0 has no per-token events, no scheduler statistics, and no feedback state. The driver observes V0 progress by polling each sequence's completion-token count after every step. Fields V0 cannot provide are recorded as `null`, never `0`.

## Workload

Traces are generated by `benchmarks/workloads.py` from a seed. Prompt tokens are uniform random ids in `[1000, 10000)`, so no tokenizer is involved. Arrivals are open-loop, with exponential gaps (Poisson). The same trace file is given to every variant for a given (scenario, `max_num_seqs`, repeat), so variants see identical arrival times and lengths.

| Scenario | Purpose |
|---|---|
| `no_contention` | few short requests; MLFQ should match FCFS |
| `slot_saturation` | long background requests fill all `max_num_seqs` slots, then short requests arrive |
| `mixed_prefill_decode` | decoding requests while new prompts of varying length arrive |
| `short_vs_long` | short and long generations mixed |
| `long_prefill_pressure` | short prompts mixed with prompts needing several prefill chunks |
| `kv_pressure` | long contexts against a KV budget (`--kv-block-budget`) |
| `starvation_aging` | fresh short requests keep arriving while older long requests wait |
| `repeated_priority_arrivals` | repeated bursts of high-priority arrivals (cooldown and thrashing) |

Background request counts scale with `max_num_seqs`, so saturation is created by the workload, not assumed. A scenario that does not reach saturation is reported as such; see the `saturation` counters in `trial.json`.

## Profiles

| Profile | Repeats | Intent |
|---|---:|---|
| `smoke` | 1 | checks that the pipeline runs end to end |
| `standard` | 3 | representative comparison (default) |
| `thorough` | 5 | larger traces |

The `thorough` profile defines a second load factor (2.0), but `run_matrix` currently uses only the first (0.5). A load-factor dimension is not part of the trial count formula. This is a known gap.

## Trial structure

- Warm-up runs (`--warmup`, default 1) use the same configuration and are stored under `raw/warmup/`. They are excluded from every statistic.
- Each measured repeat is one process that loads the model, replays the trace, and exits. Model loading is therefore outside the replay window; the replay clock starts after the engine is built.
- Trials never run concurrently. A trial that times out, crashes, or writes no `trial.json` is recorded as failed (`failed.json`) and the matrix continues.
- Latency and throughput statistics use only trials with status `ok`. Timeouts and failures are counted separately.

## Metrics

Per request (`benchmarks/metrics.py`):

- **TTFT** = first token time − arrival time.
- **E2E** = finish time − arrival time.
- **Queue wait** = admission time − arrival time.
- **TPOT** = (finish − first token) / (tokens − 1).
- **ITL** = gaps between successive token timestamps. Token timestamps are taken at the end of the engine step that produced the token, so ITL is quantized to step duration.

Per configuration: P50, P95, and P99 of these; output tokens per second; completed, unfinished, and failed counts; preemptions; peak GPU memory.

Percentiles use linear interpolation. An empty sample gives `None`. Repeats are summarized as mean, sample standard deviation, and a 95% confidence half-width (t-table for up to 10 repeats, 1.96 beyond that). Std and CI are `None` for a single repeat.

## Improvement over FCFS

- Lower-is-better metric: `(FCFS − MLFQ) / FCFS × 100`.
- Higher-is-better metric (throughput): `(MLFQ − FCFS) / FCFS × 100`.

Regressions are negative. A zero or missing baseline gives `None`.

## Output layout

```
results/experiment_YYYYMMDD_HHMMSS/
  environment.json  git_versions.json  correctness/  reports/
  bench/
    configuration.json  plan.json  traces/
    raw/<scenario>/msn<N>/<variant>/rep<k>/   trial.json requests.csv scheduler_events.csv
    raw/warmup/   logs/   summaries/
```

The report generator reads `bench/` and writes `reports/REPORT.md`, `REPORT.html`, `SUMMARY.json`, and `plots/*.png`. It never writes into its input directory. A report built from data marked `"synthetic_fixture": true` carries a banner saying so.

## Running

```bash
bash scripts/run_full_experiment.sh --max-num-seqs 8
bash scripts/run_full_experiment.sh --max-num-seqs-list 4,8,16 --profile standard --repeats 3
bash scripts/run_full_experiment.sh --dry-run --max-num-seqs-list 4,8   # CPU-only plan
```

To regenerate a report from recorded data without a GPU:

```bash
python -m benchmarks.generate_report --input results/experiment_XXXX/bench --output results/experiment_XXXX/reports
```

## Known limitations

- Latencies are measured at step granularity; ITL cannot resolve sub-step timing.
- The benchmark has not been run on a GPU. Its CUDA paths, and any performance claim, are unverified.
- Model loading is excluded, but CUDA graph capture happens during engine construction and is also excluded.
- The queue-wait-by-MLFQ-level chart is omitted: `requests.csv` has no per-request level. The report says so.
- Only one model and one GPU type are planned; conclusions do not generalize beyond them.
- `metrics_by_variant.csv` pools trials across scenarios per variant and `max_num_seqs`. This aggregation is a choice, not a requirement from the spec.
